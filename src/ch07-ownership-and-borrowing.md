# 07. 所有权与借用检查：从 PHP zval 垃圾回收理解生命周期

> “所有权系统是 Rust 最独特、最强大的创新，也是 PHP 开发者跨入系统级编程最关键的心智分水岭。”

在学习 Rust 的过程中，几乎所有动态语言背景的工程师都会在这里遭遇第一次“挫败感”——这就是著名的 **“与借用检查器（Borrow Checker）搏斗”**。

在 PHP 中，我们几乎从来不需要思考一个对象何时在内存中被销毁：
```php
function processOrder($order) {
    // 随意传递 $order，完全不用关心谁负责释放它
    doSomething($order);
    doAnotherThing($order);
}
```
PHP 的垃圾回收机制在幕后帮我们兜底了一切。

但如果你想真正掌握 Rust，就必须彻底弄清楚：**为什么 Rust 没有 GC 却能保证绝对的内存安全？它是如何做到零运行时开销的？**

本章将从 PHP 开发者最熟悉的底层原语——**Zend 引擎的 `zval` 结构体与引用计数机制**出发，通过对照的方式，带你一举攻破 Rust 的所有权与借用检查心智大关！

---

## 1. 复习：PHP 底层的内存是如何管理的？

在 PHP 7/8 中，每一个变量在底层 C 语言层面都是一个 **`zval`（Zend Value）** 结构体。

对于复杂类型（如字符串、数组、对象），`zval` 内部包含一个指针，指向具体的堆内存结构（如 `zend_string`、`zend_array`、`zend_object`）。这些底层结构头部都有一个共同的字段：**`zend_refcounted_h gc`（引用计数头）**。

```
PHP 变量 $a = new Order();
           │
           ▼
     ┌───────────┐
     │   zval    │
     ├───────────┤
     │ *u1.v     │───┐
     └───────────┘   │
                     ▼
           ┌───────────────────────┐
           │     zend_object       │
           ├───────────────────────┤
           │ refcount: 1           │  <-- 引用计数
           │ class_entry: Order    │
           │ properties: [...]     │
           └───────────────────────┘
```

当发生赋值时（如 `$b = $a;`），PHP 默认**只增加对象的引用计数（`refcount++`）**，而不复制底层内存。当函数退出或变量被 `unset()` 时，引用计数减 1（`refcount--`）。当 `refcount == 0` 时，系统在**运行时**调用 `free()` 释放内存。

### PHP 机制的代价：
1. **运行时的性能开销**：每一次变量传参、赋值、离开作用域，CPU 都要执行一次内存计数增减；
2. **循环引用问题（Circular References）**：如果对象 A 引用对象 B，对象 B 同时引用对象 A，它们的 `refcount` 永远不会归零！PHP 必须启动一个单独的**循环垃圾收集器（GC Cycle Collector）**，定期遍历根缓冲区，这会导致不可预测的延迟和 CPU 抖动。

## 2. Rust 的革命：所有权规则（The Ownership Rules）

Rust 彻底抛弃了运行时的引用计数和垃圾收集器，代之以一套在**编译期**由编译器严格执行的规则：

> ### 核心三定律：
> 1. **Rust 中的每一个值，都有一个被称为其“所有者（Owner）”的变量。**
> 2. **同一个时刻，一个值只能有且仅有一个所有者。**
> 3. **当所有者离开其所在的作用域（Scope）时，该值占用的内存将被立即自动释放。**

让我们来看一段简单的对比：

### 代码对比：
在 PHP 中：
```php
$s1 = "Hello PHP";
$s2 = $s1; // 写时复制（COW）或引用计数增加
echo $s1;  // 毫无问题，依然可用
echo $s2;  // 毫无问题
```

而在 Rust 中：
```rust
fn main() {
    let s1 = String::from("Hello Rust");
    let s2 = s1; // 发生了所有权的“移动”（Move）！

    // println!("{}", s1); // ❌ 编译报错！value borrowed here after move
    println!("{}", s2);    // ✅ 完全正常
}
```

### 为什么 `s1` 会失效？深入内存布局：
一个 `String` 对象在 Rust 内部由三部分组成（位于栈上）：**指向堆中字符数据的指针（ptr）**、**长度（len）**、**容量（capacity）**。

```
执行 let s2 = s1; 时的底层动作：
           栈（Stack）                          堆（Heap）
      ┌───────────┐
  s1  │ ptr       │───┐ (已作废)
      │ len: 10   │   │
      │ cap: 10   │   │
      └───────────┘   │               ┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
                      ├──────────────►│ H │ e │ l │ l │ o │   │ R │ u │ s │ t │
      ┌───────────┐   │               └───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
  s2  │ ptr       │───┘ (新所有者)
      │ len: 10   │
      │ cap: 10   │
      └───────────┘
```

如果允许 `s1` 和 `s2` 同时有效，当函数结束时，`s1` 和 `s2` 离开作用域，两者都会尝试去释放同一块堆内存——这就是著名的 **“双重释放（Double Free）”** 内存崩溃！

由于 Rust 没有运行时的引用计数去记录有几个人指向它，它选择在**编译期**认定：**所有权已经从 `s1` 转移（Move）给了 `s2`，从今往后 `s1` 不再合法。**

这在编译期就直接杜绝了悬垂指针与双重释放，并且**运行时开销为 0**！

## 3. 借用（Borrowing）与引用：如何在不交出所有权的前提下使用数据？

如果每次传递变量都会导致原变量失效，写代码将变得寸步难行。在现实生活中，如果我们想看朋友的一本书，我们不需要把书买下来（夺取所有权），我们只需要**借（Borrow）**来看就行了。

在 Rust 中，通过 `&` 符号创建**引用（Reference）**，这就是**借用（Borrowing）**。

### 1. 不可变借用（只读引用：`&T`）
```rust
fn calculate_length(s: &String) -> usize {
    s.len()
} // s 离开作用域，但因为它并不拥有该 String，所以不会释放堆内存

fn main() {
    let s1 = String::from("hello");
    let len = calculate_length(&s1); // 借出只读引用

    println!("'{}' 的长度是 {}", s1, len); // ✅ s1 仍然有效！
}
```

### 2. 可变借用（读写引用：`&mut T`）
如果函数需要修改被借用的值，需要声明为可变引用：
```rust
fn append_world(s: &mut String) {
    s.push_str(", world!");
}

fn main() {
    let mut s = String::from("hello");
    append_world(&mut s);
    println!("{}", s); // 输出：hello, world!
}
```

## 4. 黄金法则：读写锁原则（The Rules of References）

Rust 的借用检查器只强制执行一条终极法则，这条法则彻底消除了多线程数据竞争和迭代器失效问题：

> [!IMPORTANT]
> **在任何给定的时间，对于特定的数据，你只能拥有以下二者之一：**
> 1. **任意多个不可变引用（`&T`）（只读共享）**；
> 2. **或者，仅有且仅有一个可变引用（`&mut T`）（独占写入）**。
>
> **引用必须始终有效（生命周期内不能变成悬垂指针）。**

这就是所有后端工程师最熟悉的：**“多读单写，读写互斥”**。

### PHP 开发者最容易触发的典型编译错误：
```rust
fn main() {
    let mut s = String::from("hello");

    let r1 = &s;     // ✅ 没问题，只读借用
    let r2 = &s;     // ✅ 没问题，又一个只读借用
    // let r3 = &mut s; // ❌ 编译报错！cannot borrow `s` as mutable because it is also borrowed as immutable

    println!("{} and {}", r1, r2);
}
```
**为什么编译器要禁止它？**  
试想一下：如果 `r1` 正在读取字符串，而 `r3` 突然向字符串追加了大量字符导致底层堆内存扩容重新分配（`realloc`），那么 `r1` 指向的原内存地址就瞬间变成了**无效悬垂指针**！在 C/C++ 中这会发生未定义行为或安全崩溃，而 Rust 在编译期就坚决将其扼杀在摇篮中。

## 5. 如果确实需要多个所有者？（对标 PHP 对象的 `Rc` 与 `Arc`）

在某些复杂的图结构、缓存或多线程通信中，确实存在“多个地方共同拥有同一个对象”的诉求。

Rust 为此提供了显式的工具，而不是隐式强加给所有变量：

1. **单线程内的引用计数智能指针：`Rc<T>` (Reference Counted)**
   - 它的工作原理与 PHP 底层的 `zval` 引用计数**一模一样**！
   - 通过 `Rc::clone(&item)` 显式增加计数，离开作用域自动减计，计数归零释放内存。
2. **多线程安全的原子引用计数：`Arc<T>` (Atomically Reference Counted)**
   - 采用原子指令操作计数，可在多线程之间安全共享，这是后续开发 Tokio 异步常驻服务的基石。

## 本章小结

| 概念 | PHP 的处理方式 | Rust 的处理方式 |
| :--- | :--- | :--- |
| **内存释放时机** | 运行时 GC 动态扫描或引用计数归零 | 编译期确定作用域，离开作用域自动精准插入释放指令 |
| **赋值传递** | 复制指针 + 引用计数增加（或写时复制） | 默认发生**所有权移动（Move）**，原变量失效 |
| **传参借用** | 隐式传值/传引用（`&$arg`） | 显式不可变借用（`&T`）或可变借用（`&mut T`） |
| **数据竞争预防**| 运行时无保护，多进程/协程需手动加 Redis/锁 | 编译期**读写互斥法则**严格杜绝数据竞争 |

理解了所有权与借用检查，你就已经掌握了 Rust 最精髓的灵魂！
